# Weekly Status — лист клієнту (D11) · дефолтний стиль

> **Default** шаблон стилю + структури листа для `pmo-generate-weekly-status`.  
> Override (опційно): `docs/weekly-status/email-style.md`  
> Або явний шлях у запиті: «стиль з `path/to/style.md`».
>
> **Увага:** деякі проєкти (напр. MIT MIT) у override використовують
> короткий **cover-лист** (привітання + 3 лінки: Confluence / Timeline / Budget)
> без traffic light і без outcomes у тілі — як у реальних листах клієнту.
> Якщо існує `docs/weekly-status/email-style.md`, **його** структура має пріоритет
> над блоками нижче.

## Коли використовується

Агент готує чернетку листа decision maker клієнта. Спочатку дотримуйся **Стилю**, потім заповни плейсхолдери **Структури** з канонічних фактів проєкту (без жаргону EWS).

## Стиль

| Правило | Значення |
|---|---|
| Аудиторія | Decision Maker / PO клієнта — лише бізнес-мова |
| Довжина | ≤ 10 речень у тілі (без Subject і списків з 2–4 пунктів) |
| Тон | Спокійний, чесний, без хайпу; No Surprises |
| Мова | **Українська** за замовчуванням (інше — лише якщо Communication Plan / CONTEXT / override кажуть інакше) |
| Назви задач / тікетів | **Не вставляти англійський Jira summary як є.** Формат: `{{JIRA_KEY}}-NNN — український опис`. Якщо в Jira summary мішаний UA/EN — брати сенс українською. Допустимі власні назви продуктів (Stripe, Brevo, GraphQL) без перекладу |
| Traffic light | Завжди в Subject і в першому рядку тіла (🟢/🟡/🔴) |
| Заборонений жаргон | Без SPI, CPI, EWS, DEC, ISS, dual-role, внутрішніх назв |
| Outcomes | Краще закриті результати, ніж «працюємо над…» |
| Дати | Абсолютні (YYYY-MM-DD), не лише «наступного тижня» |
| Потрібна дія | Завжди явно: `Дій не потрібно` **або** `Будь ласка, зробіть X до Y` |
| Ризики | Простою мовою + що робимо; якщо немає — `немає` |
| Лінк на деталі | **Обов’язково** — один рядок з URL опублікованого Confluence Project Status Report. Якщо сторінки ще немає — спочатку опублікуй wiki, потім встав лінк; у фінальному листі не лишай placeholder |

## Структура (заповнити плейсхолдери)

```text
Тема: [{{PROJECT_NAME}}] Тижневий статус — {{DATE}} — {{GREEN|AMBER|RED}}

{{TRAFFIC}} Статус: {{COLOR}} — {{короткий підсумок одним рядком}}.

Цього тижня:
- {{результат 1}}
- {{результат 2}}
- {{результат 3 опційно}}
- {{результат 4 опційно}}

Наступного тижня:
- {{план 1}}
- {{план 2}}
- {{план 3 опційно}}

Ризики / блокери: {{немає | простими словами проблема + що робимо}}.

Потрібна дія: {{Дій не потрібно | Будь ласка, зробіть X до Y}}.

Детальніше у Confluence: {{CONFLUENCE_STATUS_PAGE_URL}}
```

Рядок «Детальніше у Confluence:» — лише URL (або коротка фраза + URL). Не вставляти весь wiki-текст у лист.

Формулювання світлофора в тілі (UA):

| Колір | Приклад |
|---|---|
| 🟢 | Статус: Зелений — проєкт у плані, зауважень немає |
| 🟡 | Статус: Жовтий — невелике відставання по X; наступного тижня вирівнюємо |
| 🔴 | Статус: Червоний — блокер по X; ескальовано; можливий вплив на терміни |

## Опційні блоки (лише якщо override їх увімкнув)

За замовчуванням **не** додавати:

- таблиці годин / вартості
- повні списки Jira-ключів (1–2 ключі OK, якщо клієнт уже ними користується)
- повний dump Confluence / матрицю прогресу (лінк — так; тіло звіту — ні)
- внутрішні фінанси / receivables (якщо PM явно не просить No Surprises рядок)

## Куди зберігати

Заповнений пакет тижня:

```
docs/weekly-status/{{YYYY-MM-DD}}/email.md
docs/weekly-status/{{YYYY-MM-DD}}/project-status-report.md   # wiki-тіло
docs/weekly-status/{{YYYY-MM-DD}}/draft.md                   # опційно
```

Проєктний style override (не в тижневій папці): `docs/weekly-status/email-style.md`.  
У шапці `email.md` вказати, який style-файл було використано.
