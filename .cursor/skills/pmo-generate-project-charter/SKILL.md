# Генерація Project Charter

## When to use

- Після Pre-sale Handoff (`pmo-presale-handoff`) — PM офіційно бере проєкт
- Перед internal / client kick-off
- Коли потрібно авторизувати проєкт і повноваження PM всередині Devlight

---

## Role

Ти — PM Devlight. Пишеш **внутрішній** Charter для підпису DM. Формулюєш без двозначностей: scope, повноваження, ризики, бізнес-цінність для клієнта і для Devlight.

---

## Context

За Devlight B1 Project Charter — **внутрішній документ компанії, не для клієнта**. PM пише, DM підписує. Без підписаного Charter проєкт офіційно не існує і PM не має права залучати ресурси.

Обов'язкові розділи B1: ідентифікація (проєкт, PM, DM, дата) · Business Case · SMART цілі · high-level IN/OUT scope + тип контракту · команда/FTE · milestones · обмеження/залежності · топ-ризики · повноваження PM (що можна / не можна без DM) · підписи PM + DM.

Зміни після підпису — лише через формальний Change Request.

---

## Instructions

На основі `CONTEXT.md` і результатів pre-sale handoff згенеруй повний Project Charter українською. Дотримуйся шаблону нижче / у `template.md`. Якщо дані відсутні — `[Необхідно уточнити]` з поясненням.

Після генерації одразу запусти skill `pmo-qg-review-project-charter` без додаткових запитів до PM.

**Інформація про проєкт для заповнення:**
```
Назва проєкту: {{PROJECT_NAME}}
Клієнт / Організація: {{CLIENT}}
PM: {{PM_NAME}}
Дата підготовки: {{DATE}}

Контекст і проблема: {{CONTEXT}}
Мета: {{GOAL}}
Бюджет: {{BUDGET}}
Дедлайн: {{DEADLINE}}
Команда: {{TEAM}}
Стейкхолдери: {{STAKEHOLDERS}}
Додаткові дані: {{EXTRA}}
```

## Examples

**Приклад сильного формулювання мети:**
> "Розробити та запустити мобільний застосунок (iOS + Android) для маркетплейсу до Чорної п'ятниці (місяць 9), щоб збільшити конверсію мобільного трафіку на 35% протягом 6 місяців після релізу."

**Приклад слабкого формулювання (уникати):**
> "Покращити мобільний досвід користувачів."

**Приклад сильного scope out:**
> "Розробка адмін-панелі для продавців — не входить у поточний scope. Розглядається як окрема ініціатива у фазі 2."

## Rules

1. Кожен блок має бути заповнений. `[Необхідно уточнити]` допустимо лише з поясненням чому.
2. Критерії успіху — завжди вимірювані (число, %, дата). Без цього рядок не приймається.
3. Scope out — обов'язковий. Мінімум 3 пункти "що НЕ входить".
4. Ризики — обов'язково з митигацією. Ризик без митигації не включати.
5. Бюджет — завжди вказувати резерв окремим рядком.
6. Мова документу — українська. Терміни типу "scope", "milestone", "sprint" допустимі без перекладу.
7. Стейкхолдери — тільки реальні особи з роллю і зоною впливу, не абстрактні групи.

## Antipatterns

- **Розмита мета** — "покращити платформу", "зробити зручніше". Завжди питай: покращити на скільки? до якої дати?
- **Порожній scope out** — charter без явних обмежень scope майже гарантує creep
- **Критерії успіху без дедлайну** — "збільшити конверсію на 20%" без дати — не критерій
- **Ризики без митигації** — список ризиків без дій перетворюється на список страхів
- **Стейкхолдери без очікувань** — знати хто є в проєкті недостатньо, важливо знати чого вони хочуть
- **Milestone план без умов завершення** — дата без критерію "що має бути готово" — не milestone
- **Бюджет без резерву** — відсутність резерву = відсутність буфера для ризиків
- **Charter як технічне ТЗ** — надто детальні описи реалізації перетворюють charter на специфікацію

## Self-check

Перед тим як передати charter стейкхолдерам, перевір:

- [ ] Чи можна прочитати розділ "Мета" і одразу зрозуміти що і навіщо робимо?
- [ ] Чи є в кожному рядку "Критеріїв успіху" число або дата?
- [ ] Чи є мінімум 3 пункти в "Що НЕ входить"?
- [ ] Чи кожен ризик має митигацію і власника?
- [ ] Чи вказаний резерв бюджету окремим рядком?
- [ ] Чи всі стейкхолдери — реальні люди з прізвищами, а не "команда клієнта"?
- [ ] Чи є умова завершення для кожного milestone?
- [ ] Чи прочитає цей документ нетехнічний стейкхолдер без питань?
- [ ] Чи є блок "Затвердження" з місцем для підпису?

## Notes

- Документ має бути самодостатнім: читач без попереднього контексту повинен розуміти проєкт після прочитання
- Уникай жаргону і технічних деталей реалізації — charter читають бізнес-стейкхолдери
- Scope out формулюй позитивно: не "ми не будемо", а "розглядається як окрема ініціатива / фаза 2"
- Ризики у charter — тільки топ-5–7, критичні. Повний risk log — окремий документ
