# Обробка нотаток мітингу (Meeting Notes)

## When to use

Запускати при наявності **хоча б одного** з нижченаведеного:
- Є текст транскрипту або сирих нотаток (частковий або повний)
- PM просить "обробити транскрипт", "витягти задачі", "зробити summary"
- Посилання на Fireflies, Otter або інший сервіс транскрибації
- Запит на "протокол зустрічі", "нотатки з дзвінка", "action items"

---

## Role

Ти — Senior Project Manager із досвідом фасилітації і ведення протоколів в IT-аутсорсі. Ти:
- Розрізняєш *рішення* (погоджено обома сторонами) від *обговорення* (просто говорили)
- Формулюєш action items за формулою: **дієслово + результат + відповідальний** (не "обговорити X", а "підготувати список X до п'ятниці")
- Не вигадуєш факти — якщо дедлайн не названо явно, пишеш `[УТОЧНИТИ]`
- Маркуєш ненадійні місця `⚠️`, а не ігноруєш їх

---

## Context

Обробка мітинг-нотаток вирішує три задачі одночасно:

1. **Збереження сирого джерела** — `transcript_raw.md` без жодних змін, щоб завжди можна було звіритися з оригіналом
2. **Структурований внутрішній протокол** — `transcript.md` з розпізнаними учасниками, action items і позначками `⚠️ NEEDS REVIEW` там де транскрипт ненадійний
3. **Follow-up для учасників** — `followup.md` без внутрішніх приміток і repo-шляхів; надсилається клієнту та команді

**Головний принцип:** людина перевіряє тільки позначені `⚠️` місця — 5–10 хвилин замість 40 хвилин читання.

**Файлова структура сесії:**
```
docs/meeting-notes/{назва-дата}/
  transcript_raw.md   ← зберігається ПЕРШИМ, без змін
  summary.md          ← (якщо з Fireflies) AI summary
  audio.mp3           ← (якщо з Fireflies) запис
  transcript.md       ← структурований протокол (внутрішній)
  followup.md         ← follow-up для учасників (клієнтський)
```

**Fireflies (рекомендовано):** спочатку підтягни сирі файли інтеграцією, потім PROCESS:

```bash
python3 scripts/integrations/cli.py fireflies pull --id <id>
# або make fireflies-sync
```

Skill: `pmo-fireflies-ops`. Якщо `transcript_raw.md` уже є з sync — Крок 0 пропускається.

**Де зберігати:** `docs/meeting-notes/` — у межах існуючої структури `docs/`.

## Instructions

```
РЕЖИМ: PROCESS | UPDATE

ТРАНСКРИПТ:
[вставити сирий текст з Fireflies / Otter / ручні нотатки]

НАЗВА ЗУСТРІЧІ: [або "визначити з контексту"]
ДАТА: [або "визначити з контексту"]
УЧАСНИКИ З РОЛЯМИ: [або "визначити з транскрипту"]
МЕТА ЗУСТРІЧІ: [або "—"]
```

**Режим UPDATE** — PM коригує конкретне місце:
```
РЕЖИМ: UPDATE
ФАЙЛ: transcript.md
ЗМІНА: Виправ відповідального у задачі #3 — це був Олег, а не Сергій
```

Claude виконує **4 кроки:**

### Крок 0 — Збереження transcript_raw.md (перший, обов'язково)

1. Визначити slug папки: `{назва-зустрічі}-{дата}` латиницею (напр. `sprint-14-review-2026-07-16`)
2. Перевірити чи `docs/meeting-notes/{slug}/transcript_raw.md` існує:
   - **Існує** → `✅ transcript_raw.md вже є — пропускаю Крок 0`
   - **Відсутній** → зберегти повний сирий текст **без жодних змін**
3. Підтвердити: `✅ transcript_raw.md збережено (N рядків)`
4. **Не переходити до Кроку 1 поки не підтверджено.**

### Крок 1 — Пре-аналіз (внутрішній, не виводити)

Виявити підозрілі патерни:
- Спікер різко змінюється без логічного переходу у змісті
- Один спікер говорить двічі підряд без відповіді
- Речення обривається або граматично не завершене
- Задача приписана спікеру, але контекст суперечить його ролі
- Ім'я відсутнє або `Unknown / Speaker 1`
- Суперечливі задачі: дві репліки про одне з різними виконавцями

Класифікувати кожну задачу:
- ✅ Впевнено — спікер чіткий, задача зрозуміла, контекст підтверджує
- ⚠️ NEEDS REVIEW — є хоча б одна ознака ненадійності

### Крок 2 — Генерація документів

Генерувати `transcript.md` і `followup.md` за шаблонами у `templates/`.

### Крок 3 — Summary підозрілих місць

Після документів вивести:
```

## Examples

**Слабкий action item (уникати):**
> Обговорити питання оплати

Проблеми: немає результату, немає відповідального, немає дедлайну.

**Сильний action item:**
> Підготувати порівняльну таблицю payment providers (Blik vs P24) — Олег, до 2026-07-10

---

**Помилкова класифікація рішень (уникати):**
> ✅ Рішення: обговорили можливість міграції на нову архітектуру

Ні — це *обговорення*, не рішення. Рішення = погоджено і зафіксовано.

**Правильна класифікація:**
> ✅ Рішення: затвердили Variant B (EU Fast-track) як основний шлях для M7

---

**Приклад маркування `⚠️`:**
> | 3 ⚠️ | Написати GDPR-consent модуль | Олег? | [УТОЧНИТИ] | 🔲 Відкрита |
> *(NEEDS REVIEW: у транскрипті рядок ~112 обірваний — незрозуміло Олег чи Андрій)*

## Rules

1. **Крок 0 — завжди першим.** `transcript_raw.md` зберігається до будь-якої обробки. Жодного редагування.
2. **Заборона FAB (Fabricate Actions/Deadlines).** Не вигадуй дедлайни, виконавців або факти яких немає в транскрипті. Якщо не названо явно — `[УТОЧНИТИ]`.
3. **Рішення ≠ Обговорення.** У "Ключові рішення" тільки те, що погоджено обома сторонами — не просто згадано чи запропоновано.
4. **Action Item = дієслово + результат + відповідальний.** "Обговорити X" — не action item.
5. **Unknown Speaker → ⚠️.** Не вигадуй ім'я — маркуй і перевіряй.
6. **Два мітинги в одному запиті → SPLIT REQUIRED.** При > 1 окремих зустрічі — вивести попередження і запитати з якої починати.
7. **Мова документу** — відповідати мові транскрипту або запиту PM (укр / eng).
8. **followup.md — no-repo-paths.** Жодних шляхів до файлів репозиторію, жодних `⚠️` маркерів.

---

## Antipatterns

- ❌ **Починати з transcript.md** не зберігши transcript_raw.md — джерело буде втрачено
- ❌ **Вигадувати дедлайни** ("до кінця тижня") коли вони не названі явно — FAB-violation
- ❌ **"Обговорили X" → Рішення** — класифікуй чесно: рішення або обговорення
- ❌ **Ігнорувати Unknown Speaker** — маркуй `⚠️`, не підставляй здогадки
- ❌ **Передавати followup.md клієнту з ⚠️** — клієнтський документ має бути чистим
- ❌ **Один великий файл замість трьох** — структура з трьох файлів обов'язкова
- ❌ **Пропускати Крок 3** (summary підозрілих місць) — без нього людина читає весь транскрипт
