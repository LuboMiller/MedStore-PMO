# Project Status Report (HTML Dashboard)

## When to use

- **Щотижня / після sprint review** — оновити дашборд для стейкхолдерів
- **На запит клієнта або C-level** — quick visual overview стану проєкту
- **Перед steering committee** — поточний snapshot EVM, velocity, ризики, roadmap

---

## Role

Ти — Senior Project Manager + Data Analyst. Ти читаєш дані з кількох джерел, розраховуєш EVM-метрики, визначаєш RAG-статус проєкту та генеруєш HTML-дашборд, який є єдиним джерелом правди про стан проєкту для стейкхолдерів.

---

## Context

Project Status Report — це HTML-дашборд, який в одному вигляді показує: графік velocity, EVM-метрики (CPI, SPI, EAC, VAC), активні ризики та milestone map. Призначений для C-level та клієнта — читається за 30 секунд, дає відповідь на три питання: **чи в бюджеті, чи в графіку, що загрожує завершенню.**

Файл знаходиться у `dashboards/project-status-dashboard.html` і перегенерується при кожному оновленні. Шаблон — `templates/tl-project-status-dashboard.html` із `{{PLACEHOLDER}}`-змінними.

**Джерела даних:**
- `dashboards/sprint-tracker.md` — velocity, SP факт, поточний спринт (запустити `make sync-tracker` перед генерацією)
- `docs/risk-register.md` — активні ризики (critical / high count + усі ризики з мітігацією), включно з колонками "Дата появи" / "Останнє оновлення"
- `CONTEXT.md` — команда, дедлайни, бюджет BAC, EVM-базис, фази проєкту (для Gantt)
- `dashboards/roadmap.md` — milestones і їх статус (для Gantt)
- `docs/evm-log.md` — **канонічний журнал EVM-знімків**; цей промпт є єдиним, хто туди пише

**EVM формули:**
```
PV  = (накоп. SP плановий / total SP) × BAC
EV  = (накоп. SP факт / total SP) × BAC
AC  = спринтів × $/спринт
CPI = EV / AC          (< 1.0 = over budget)
SPI = EV / PV          (< 1.0 = behind schedule)
EAC = BAC / CPI        (прогноз фінальної вартості)
VAC = BAC − EAC        (від'ємне = cost overrun)
SV(днів) ≈ (SPI − 1) × T   (T = календарних днів від kick-off до reporting cutoff; спрощена оцінка, не повна Earned Schedule методологія)
```

**SV(днів) — бізнес-переклад SPI, окремим тайлом.** Так само як CPI завжди супроводжується VAC у доларах (щоб нетехнічний стейкхолдер відчув вплив на бюджет), SPI завжди супроводжується SV у днях (щоб відчув вплив на дедлайн). На відміну від VAC (який лишається рядком усередині тайла EAC), **SV — окремий `.perf`-тайл одразу після SPI** в `.perf-band`, а не бейдж і не підрядок усередині тайла SPI — саме так було явно запитано, і це найпростіший спосіб гарантувати, що SV не загубиться серед іншого тексту. Приклад: SPI 0.960, T = 195 днів → SV ≈ −8 днів. Це оцінка відставання **на сьогодні**, окремо від `{{SCHEDULE_DELTA_DAYS}}` (прогнозоване відставання **на момент завершення проєкту** при збереженні поточного темпу) — обидва числа легітимні, але означають різне; не плутати.

**Колір SV — незалежний від кольору SPI, за таблицею порогів нижче, не дзеркалення.** Аналогія: VAC поруч з CPI має власну (напрямкову) логіку кольору, а не копіює клас CPI — CPI=0.942 фарбується `metric-warn`, а VAC=−$26,582 незалежно фарбується `delta-over` (червоний), і це нормально, бо вони відповідають на різні питання. SV так само: сенс SV — показати в днях те, що ratio-based поріг SPI (≥0.95 при будь-якій тривалості проєкту) може ховати на довгих проєктах. Якщо фарбувати SV кольором SPI, SV перетворюється на декоративний дублікат і втрачає власний сигнал. Тому SV отримує власний поріг у днях, прив'язаний до тривалості спринту (14 днів) — природна, пояснювана одиниця для цього проєкту.

**Правило межі спринту:** EVM перераховується **тільки коли поточний спринт закрився** (SP Факт у sprint-tracker перейшов з "—" на число). Якщо звітна дата припадає на спринт, що ще триває — CPI/SPI/EAC/VAC копіюються з останнього рядка `docs/evm-log.md` без змін; перераховувати "на око" мід-спринту заборонено (EV не рухається, доки SP не зараховано, а AC мід-спринту тільки росте — тобто "покращення" CPI без закриття спринту завжди помилка).

**Де зберігається результат:** `dashboards/project-status-dashboard.html` (артефакт) + новий рядок у `docs/evm-log.md` (канонічне джерело)

Claude виконує:

1. **`make sync-tracker`** — оновити `dashboards/sprint-tracker.md` перед читанням
2. **Читає** `dashboards/sprint-tracker.md` — поточний спринт, velocity, накоп. SP
3. **Читає** `CONTEXT.md` — BAC, total SP, дати, команда
4. **Читає** `docs/risk-register.md` — critical / high count, топ-5 ризиків **з полями Категорія та Мітігація**; для 🔴/🟡 ризиків додатково читає секцію **Mitigation Plan** (поле Contingency)
5. **Читає** `dashboards/roadmap.md` — milestones, статус кожного; фази та дати для Gantt chart
6. **Читає** `docs/evm-log.md` — останній рядок
7. **Розраховує EVM** — якщо поточний спринт щойно закрився (SP Факт з'явився) — рахує PV/EV/AC/CPI/SPI/EAC/VAC/SV(днів) за формулами і **додає новий рядок у `docs/evm-log.md`**. Якщо спринт ще триває — копіює CPI/SPI/EAC/VAC/SV(днів) з останнього рядка `docs/evm-log.md` без перерахунку.
8. **Визначає RAG** — за логікою вище
9. **Генерує SVG** — velocity sparkline тільки для закритих спринтів
10. **Замінює `{{PLACEHOLDER}}`** у шаблоні → зберігає в `dashboards/project-status-dashboard.html`
11. **Перед фінальним збереженням** — прогнати `skill `pmo-qg-review-status-consistency`` разом з будь-якими іншими артефактами того ж публікаційного циклу (client/team/deck за ту саму дату)

## Rules

1. **EVM — точні формули.** CPI = EV/AC, SPI = EV/PV. Не rounded до 2 знаків — саме такий формат.
2. **RAG визначається програмно** — не "відчуття", а конкретні пороги CPI/SPI/ризиків.
3. **Velocity SVG** — тільки закриті спринти. Активний — окрема крапка. Майбутні — не відображати.
4. **Top-5 ризиків** — сортувати: спочатку critical (за Score DESC), потім high. Брати з `risk-register.md`. Для кожного обов'язково: Категорія, Мітігація (~80 символів) та Contingency з секції Mitigation Plan (~80 символів).
5. **Milestones** — показувати всі фази; статус `done/active/plan/risk` визначати за датою та наявністю блокерів.
6. **Таблиця спринтів** — останні 3 завершені + активний + наступний (5 рядків).
7. **Gantt chart** — Canvas-based, 6 рядків (фази проєкту). Дати фаз беруться з CONTEXT.md / roadmap.md. Якщо дати змінились — оновити масиви `PHASES` і `MILESTONES` у JS-блоці Gantt у файлі HTML. TODAY hardcoded — оновлювати при кожній регенерації.
8. **Не редагувати вручну** — тільки через цей промпт. HTML — артефакт, а не джерело правди.
9. **EVM тільки на межі спринту.** Мід-спринту CPI/SPI/EAC/VAC/SV не перераховуються — копіюються з останнього рядка `docs/evm-log.md`. Новий рядок у лог додається лише коли спринт формально закрився.
10. **`docs/evm-log.md` — єдине джерело правди для EVM.** Дашборд і всі status-звіти (pm-15) мають показувати числа, ідентичні останньому рядку логу; будь-яка розбіжність — блокер на `pm-qg-05`.
11. **SPI завжди з SV(днів) поруч, як окремий `.perf`-тайл одразу після SPI** — не бейдж і не рядок усередині тайла SPI, а власний блок у сітці `.perf-band`, той самий рівень видимості що й будь-яка інша метрика (CPI, EAC, Bug Count). Голий індекс без перекладу в дні — неповний дашборд.
12. **Одна мова в межах одного речення.** Документ пишеться українською (`CLAUDE.md`). Універсальні абревіатури (CPI, SPI, EAC, VAC, SV, US-NN, CR-NN) лишаються як є, але решта тексту в тому самому `.kpi-sub`/реченні — послідовно одна мова. Не "перенесено з Sprint 14 close" (мовний мікс) — або повністю українською ("перенесено із закриття Sprint 14"), або повністю англійською, не обидва в одному реченні.
13. **Якщо дашборд містить текстову рекомендацію PM (наративний блок поза `{{PLACEHOLDER}}`-таблицею)** — рекомендовані дії щодо активних ризиків мають посилатись на конкретний запис у колонці "Митигація" `docs/risk-register.md`, а не формулюватись загально ("домовитись", "узгодити") без конкретики вже затвердженого плану.
14. **Жодного кольору "на відчуття" або хардкоду.** Кожен `metric-*` клас і кожен колір заливки (`{{PCT_BUDGET_BAR_COLOR}}`, `{{COST_CR_COLOR}}`, `{{METRIC_BUG_RATE_BAR_COLOR}}` тощо) обчислюється за таблицею порогів вище з фактичного значення. Ніколи не писати `background:var(--warn)` напряму в HTML — тільки через `{{PLACEHOLDER}}`, інакше колір "застигає" і перестає відповідати даним при наступній регенерації.

## Antipatterns

- **Ручне редагування HTML** — при наступній генерації перезапишеться; джерела правди — md-файли.
- **RAG без цифр** — "проєкт під ризиком" без CPI/SPI не дає стейкхолдеру розуміння масштабу.
- **Velocity chart без закритих спринтів** — якщо chart порожній, перевірити чи `make sync-tracker` запускався.
- **EAC без пояснення** — завжди показувати `VAC` поряд з `EAC`, щоб був видний overrun.
- **Milestone "In progress" без дати** — кожен milestone має дату або sprint range.
- **Ризики без мітігації і contingency** — стейкхолдер після "що загрожує" питає "що ми робимо" і "що якщо не допоможе"; обидві відповіді мають бути в тому ж рядку.
- **SPI без SV** — "SPI 0.98" нічого не каже нетехнічному стейкхолдеру (CMO); завжди поруч переклад у дні, як VAC поруч з CPI.
- **SV захований усередині SPI-тайла (текстом у `.kpi-sub` або бейджем у тому ж блоці)** — SV має бути власним `.perf`-тайлом одразу після SPI в сітці, щоб його було видно з першого погляду серед інших метрик, а не вчитуватись у підпис SPI.
- **Мовний мікс в одному реченні** — "перенесено з Sprint 14 close" (українська + англійське слово) виглядає недбало; одна мова на речення.
- **Generic PM-рекомендація замість посилання на Митигацію** — "домовитись по Х" коли реєстр вже має конкретний затверджений план — виглядає так, ніби рішення ще не ухвалено.
- **Хардкоджений колір (`background:var(--warn)` прямо в HTML)** — застигає назавжди, навіть коли Budget Completion опуститься нижче Project Completion і насправді стане "ok". Завжди `{{PLACEHOLDER}}`, обчислений з таблиці порогів.
- **Колір, що суперечить власному чекмарку** — "$7,000 ✅" пофарбований у critical/bad виглядає як тривога поруч із підтвердженням; для CR Cost колір відображає % резерву, а не факт підтвердження (яке й так показане ✅).
