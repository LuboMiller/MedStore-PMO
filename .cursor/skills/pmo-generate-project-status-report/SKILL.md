# Project Status Report (Текстовий — CLIENT / TEAM / DECK)

## When to use

- **Щотижня / після sprint review** — генерує всі три формати одночасно: CLIENT + TEAM + DECK

---

## Role

Ти — Senior Project Manager із досвідом клієнтської комунікації в IT-аутсорсі. Ти вмієш:
- Перекладати технічні факти у бізнес-мову (для клієнта)
- Давати гранично конкретну операційну інформацію без прикрас (для команди)
- Стискати суть до 3–4 слайдів без втрати критичної інформації (для deck)

---

## Context

Project Status Report у текстовому форматі вирішує три різні задачі залежно від аудиторії:

1. **CLIENT** — статус для замовника: **бізнес-оптика**. Акцент на impact, ризиках, дедлайнах, наступних кроках. Мінімум технічних деталей — максимум релевантності для прийняття рішень клієнтом.

2. **TEAM** — статус для команди: **операційна ясність**. Акцент на що зроблено, що зараз у процесі, блокерах, конкретних наступних діях. Без красивих формулювань для бізнесу.

3. **DECK** — status-презентація: **3–4 слайди за 15 хвилин**. Проста, робоча структура, яку PM може зібрати швидко для будь-якої аудиторії. Формат: Progress / Risks / Next або Timeline / Risks & Mitigations / Decisions Needed.

**Джерела даних:**
- `dashboards/sprint-tracker.md` — поточний спринт, velocity, SP факт vs план
- `docs/risk-register.md` — активні ризики з мітігацією (+ "Дата появи" / "Останнє оновлення" якщо звіт це згадує)
- `docs/evm-log.md` — CPI/SPI/EAC/VAC (**канонічне джерело — не перераховувати самостійно**, брати останній рядок)
- `docs/change-requests/CR-NN-*.md` — статус і дата рішення будь-якого CR, згаданого у звіті
- `CONTEXT.md` — дедлайни, бюджет, команда, milestones
- `dashboards/roadmap.md` — статус milestones

**Reporting cutoff:** дата зрізу даних (`{дата}` у заголовку CLIENT/TEAM, `{{DECK_DATE}}` у DECK) має бути **ідентичною** у всіх трьох документах одного циклу і збігатись з `{{REPORT_DATE}}` дашборду (pm-14), якщо генеруються разом. Це не дата запуску генерації — це дата, на яку актуальні дані.

**Де зберігається результат:** усі три файли в **директорії циклу**  
`docs/status-reports/{YYYY-MM-DD}/client-{YYYY-MM-DD}.md`,  
`team-{YYYY-MM-DD}.md`, `deck-{YYYY-MM-DD}.md` (не в корені `status-reports/`).

D11 cover + Confluence wiki-тіло для клієнтської п’ятниці — окремо в  
`docs/weekly-status/{YYYY-MM-DD}/` (`pmo-generate-weekly-status`).

## Instructions

```
ЗВІТНА ДАТА: [DD Mon YYYY або "сьогодні"]
ПОТОЧНИЙ СПРИНТ: [N або "визначити з контексту"]
КЛЮЧОВІ ОНОВЛЕННЯ: [нові ризики, milestone зміни, scope changes — або "—"]
```

Claude виконує:

1. **Читає** `CONTEXT.md` — BAC, дедлайни, milestones, команда
2. **Читає** `dashboards/sprint-tracker.md` — поточний спринт, velocity, SP прогрес
3. **Читає** `docs/risk-register.md` — топ-ризики з Категорією та Мітігацією (основна таблиця); Contingency для 🔴/🟡 ризиків — з секції **Mitigation Plan**. Ці ж формулювання Митигації використовує для Next Actions, що стосуються цих ризиків
4. **Читає** `docs/evm-log.md` — останній рядок для CPI/SPI/EAC/VAC та SV (днів), якщо звіт їх згадує
5. **Читає** `docs/change-requests/CR-NN-*.md` для будь-якого CR, згаданого у звіті — статус і дата рішення мають збігатись з тим, що там записано
6. **Читає** `dashboards/roadmap.md` — статус milestones
7. **Генерує всі три документи** відповідно до шаблонів нижче: CLIENT → TEAM → DECK, з однаковим reporting cutoff у всіх трьох
8. **Прогонає** `skill `pmo-qg-review-status-consistency`` перед збереженням — разом з дашбордом (pm-14), якщо генеруються в тому ж циклі
9. **Зберігає** всі три у `docs/status-reports/{YYYY-MM-DD}/` та конвертує у PDF командами з блоку OUTPUT

## Examples

**CLIENT — слабко (уникати):**
> Sprint 14 закрили з velocity 38 SP замість 45 SP. CPI = 0.945.

Клієнт не знає що таке SP або CPI — ця інформація марна для прийняття рішень.

**CLIENT — сильно:**
> Виконано 47% продукту. Поточний темп дає ризик затримки фінального запуску на ~2 тижні. Ми вже ввели додаткові code review сесії для стабілізації темпу.

---

**TEAM — слабко:**
> Проєкт розвивається відповідно до бізнес-цілей. Команда демонструє залученість.

Це нічого не говорить команді що робити завтра.

**TEAM — сильно:**
> Sprint 14: закрили 38/45 SP. Блокер: API інтеграція з POS затягнулась — Олег очікує відповідь від вендора до середи. Sprint 15 фокус: checkout flow + GDPR-consent.

---

**DECK — слабко:**
> Slide 1: "Project Overview" · Slide 2: "Team Update" · Slide 3: "Next Steps"

Generic структура без конкретики — не дає нічого.

**DECK — сильно:**
> Slide 1: 47% complete · M3 on track · M4 at risk (+2w)
> Slide 2: R-02 POS API delay (High) · R-08 GDPR gap (Critical)
> Slide 3: Decision needed — EU Fast-track vs Standard? → Client by 2026-07-14

## Rules

1. **CLIENT — заборона jargon.** SP, CPI, SPI — не використовувати без пояснення. Переводь у бізнес-мову: "47% виконано", "ризик затримки на 2 тижні", "на $18K більше за план".
2. **TEAM — конкретні факти, не сантименти.** "Команда попрацювала добре" — не пишемо. Пишемо: "38/45 SP закрито, блокер на checkout — вирішується до середи".
3. **DECK — максимум 4 слайди.** Якщо не вміщується — скорочуй, не додавай слайди.
4. **Ризики з мітігацією завжди.** Ніколи не вказувати ризик без "що ми вже робимо".
5. **RAG — за порогами з pm-14.** `GREEN`: CPI ≥ 0.95 AND SPI ≥ 0.95 AND ≤ 3 critical. `AMBER`: CPI 0.85–0.95 OR SPI 0.85–0.95. `RED`: CPI < 0.85 OR milestone прострочений.
6. **Дати — абсолютні.** "Незабаром" або "наступного тижня" — заборонено. Якщо невідомо — `[УТОЧНИТИ]`.
7. **Decisions needed — явно відділяти від інформації.** Якщо від стейкхолдера нічого не потрібно — написати це прямо.
8. **Reporting cutoff однаковий скрізь.** CLIENT, TEAM, DECK (і дашборд, якщо генеруються разом) показують ту саму дату зрізу даних — не дату запуску кожного окремого файлу.
9. **EVM не перераховувати.** CPI/SPI/EAC/VAC — тільки з останнього рядка `docs/evm-log.md`. Якщо цифри "не сходяться" з очікуванням — це сигнал звірити з логом, не привід порахувати самостійно.
10. **CR статус — з CR-документа.** Якщо звіт згадує CR, дата рішення і статус мають дослівно збігатись з `docs/change-requests/CR-NN-*.md`, не переказуватись "по пам'яті".
11. **Next Actions прив'язані до Митигації.** Якщо рекомендована дія стосується активного ризику з `docs/risk-register.md` — формулювання береться з колонки "Митигація" (або "Mitigation Plan" для 🔴/🟡) дослівно чи близьким перефразуванням, а не вигадується заново. Генеральні формулювання ("домовитись", "зустрітися", "обговорити") без конкретики з реєстру — заборонені для дій, що вже мають затверджену митигацію.
12. **SPI завжди з бізнес-перекладом.** Якщо TEAM (або будь-який звіт) показує SPI як індекс — поруч обов'язково текстовий еквівалент у днях (SV, з `docs/evm-log.md`), напр. "SPI 0.960 (≈ -8 днів графіку)" — не голий індекс без пояснення що він означає для дедлайну.

## Antipatterns

- ❌ **Один статус для всіх** — клієнт і команда читають різний контент з різними акцентами
- ❌ **"Проєкт розвивається успішно" без цифр** — загальні слова замість фактів
- ❌ **DECK з > 4 слайдами** — якщо більше 4, це вже не "15-хвилинний deck"
- ❌ **Ризики без мітігації** — тривога без відповіді на "що ми з цим робимо"
- ❌ **Технічні деталі в CLIENT** — "POS API timeout 3000ms" — не для клієнта
- ❌ **Бізнес-мова в TEAM** — "продукт демонструє позитивну динаміку" — не для команди
- ❌ **Відносні дати** — "наступний вівторок" замість "2026-07-14"
- ❌ **Generic Next Action замість затвердженої митигації** — "домовитись по Blik/P24" коли реєстр вже каже "перехід на backup-агрегатор Przelewy24 Partner API" — переформулювання втрачає конкретику вже прийнятого рішення
- ❌ **Голий SPI/CPI без бізнес-перекладу** — "SPI 0.98" нічого не каже CMO; поруч завжди SV у днях або аналогічний VAC-подібний переклад у гроші/час
